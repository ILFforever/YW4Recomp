# 0010 — Loader and import stubs (Phase 3 skeleton)

Date: 2026-10-21
Status: accepted

## Decision

`python -m recomp.translate` also writes `work/recomp/image_info.c`: the tables the loader needs, all generated by the tested Python readers in `tools/yw4/`. `python -m recomp.build` compiles everything into `work/build/yw4.exe`, which takes the path to `main.bin` on the command line.

**Image bytes are never built in.** The executable reads `work/exefs/main.bin` at start-up and refuses it unless both the size and the SHA-256 match the build it was recompiled from. That is the version lock again (CLAUDE.md rule 3), enforced by the runtime itself (`runtime/src/sha256.c`, tested against `hashlib`).

**Memory.** One block holds the image and its `.bss`: 0x6AE9000 bytes, about 112 MB, 90 MB of it `.bss`. It is placed at **`0x7100000000`, main's address on the Switch**, and falls back to anywhere if that range is taken. Guest stacks go to `0x7000000000`. Reasons:
- Everything stays inside the 39-bit address space a Switch game may assume (CLAUDE.md, Phase 1 note). The first run without this put the stack at `0x288…` (41 bits).
- Logged addresses equal Ghidra's addresses, which makes debugging easier.

**Relocations** (measured in `main`):

| Type | Count | Applied as |
|---|---|---|
| RELATIVE | 56,775 | image base + addend |
| ABS64 | 4,253 | import address + addend |
| JUMP_SLOT | 551 | import address |
| GLOB_DAT | 19 | import address |

**Imports** (578, all referenced):
- **554 functions.** Each gets a unique address in a stub region. `yw4_resolve` maps that address, through a lookup hook, to a generated `imp_<i>`, which calls `yw4_import_call(ctx, i)`. That runs a native implementation found by mangled name, or stops with the import's name and the guest address of the call. Function pointers to imports (e.g. in vtables) work the same way, because every indirect call goes through `yw4_resolve`.
- **20 data objects** (C++ type-info vtables, the fundamental type infos, `stdin`/`stdout`/`stderr`). Each gets a zeroed 4 KiB block until their implementations fill them.
- **4 weak symbols that nobody exports** (`__rel_dyn_start` and similar linker markers) resolve to 0.

**Start-up order**, as in the Nintendo SDK:
1. `nninitStartup`: the game's memory set-up hook, called before static constructors;
2. `DT_INIT` (`main+0x30`), which calls `__nnmusl_init_dso` and then runs the 830 `.init_array` constructors;
3. `nnMain`.

## Result (2026-10-21)

```
yw4: main loaded at 0000007100000000 (its Switch address), 61598 relocations, 578 imports (20 data)
yw4: running nninitStartup (main+0x94eb50)
yw4: unimplemented import #157 _ZN2nn2os15QueryMemoryInfoEPNS0_10MemoryInfoE
     called from main+0x94eb6c with x0=0x70007fff98 x1=0 x2=0
```

Recompiled code runs natively until its first `sdk` call. That call sits exactly where the disassembly says it does.

The imports each stage calls directly (static scan):
- `nninitStartup`: `nn::os::QueryMemoryInfo`, `SetMemoryHeapSize`, `AllocateMemoryBlock`, plus `nn::diag` logging/asserts;
- `DT_INIT`: `__nnmusl_init_dso`;
- `nnMain`: `GetHostArgc`/`GetHostArgv`, `GetSystemTick`, `__cxa_guard_acquire`/`release`, `SleepThread`.

## Open

- Implementations go in `runtime/src/hle.c`'s table for now; split by `nn::` namespace once there are more than a handful.
- The 20 data imports need real contents before RTTI, `dynamic_cast` or stdio are used.
- Guest stack size is a fixed 8 MB; take it from the NPDM later.
- Threads: one guest thread only (`nn::os::CreateThread` will need per-thread `CPUState` and stacks, plus TLS).
- Build speed: a full Clang `-O1` build of the 88 files takes about 4 minutes. A change to a runtime header recompiles everything, because generated code includes `yw4rt.h`.
