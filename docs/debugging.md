# Run options and debugging

Environment variables and keys read by the runtime. The game runs fine with none of them set. Tools that run the
game with them and compare results: [tools/dev](../tools/dev/README.md).

Which build is running ([decision 0047](decisions/0047-versioning.md)): `yw4 --version` prints one line
(`YW4 Recomp 0.7.0 (a8b8184, built 2026-11-03)`) without starting the game; the log's first lines and the
window title say the same. The number is the repo's `VERSION` file; `+dirty` means uncommitted changes.

Where the game looks for its own files ([decision 0048](decisions/0048-home-folder-and-icon.md)): every `work/...`
path is relative to its home folder, which it changes to at start (the log's `yw4: home` line): `YW4_HOME=<folder>`
if set, else the folder above `work/` when `yw4.exe` is in `<home>/work/build/`. Relative paths in the variables
below are relative to it too. The three folders on the command line are made absolute first.

Started with no arguments (a double-click, a shortcut), the game reads `game.ini` next to `yw4.exe`
([decision 0050](decisions/0050-launcher-and-install-layout.md)): one `YW4_...=value` per line, any variable on
this page, plus `YW4_EXEFS`, `YW4_ROMFS` and `YW4_SAVE` for the three folders. Paths are relative to `game.ini`'s
folder; a variable already in the environment wins. Without it a message says to run the launcher.

For reports from other PCs, the log's `window:` lines near the start name the GPU, the driver and its version
(`driver radv, Mesa 25.1.4`), the window system (`windows`, `wayland`, `x11`) and every screen format the driver
offers as `format/colour space` numbers (Vulkan's `VkFormat` / `VkColorSpaceKHR`: 44 = B8G8R8A8_UNORM,
37 = R8G8B8A8_UNORM, 50 = B8G8R8A8_SRGB; colour space 0 = sRGB, others are HDR, extended or linear ones). The
game uses an 8-bit UNORM format in colour space 0; any other choice makes the colours look wrong (pale), and the
line then says WARNING.

## Everyday options

| Variable | What it does |
|---|---|
| `YW4_SETTINGS_FILE=<file>` (`none`) | Where the settings panel's choices are kept (default `settings.ini` next to `yw4.exe`): read at start, written on every change in the panel, one `YW4_...=value` line per setting. A variable set in the environment wins over its line. `tools.dev.run` sets `none`, so test runs neither read nor change the owner's file |
| `YW4_FIRST_RUN_LEVEL=low` (`high`) | Tests: a new install's first start (no settings file yet: point `YW4_SETTINGS_FILE` at a file that doesn't exist) as on that kind of GPU. Without it the GPU decides: integrated, or under 4 GB of video memory, is low (shadow map 1024, soft and contact shadows off, effects half); else the high defaults stay. The file is then written, so it runs once, and a notice fades in at the top for about 6 s (screenshots include it). [Decision 0062](decisions/0062-first-start-graphics.md) |
| `YW4_SCREENSHOTS=600,2500` | Save a screenshot at these frame numbers (also F12 at any time) |
| `YW4_SCREENSHOT_DIR=path` | Where screenshots go (default `<work_dir>/screenshots/`) |
| `YW4_THEME=id` | The overlay's and the HUD's theme (Settings > Look > Theme, saved in settings.ini): `recomp` (built in) or a file's name in the themes folder, e.g. `jibanyan` ([decision 0055](decisions/0055-overlay-themes.md)) |
| `YW4_THEMES_DIR=path` | The themes folder (the launcher's `.css` files); else `themes` next to yw4.exe, else the repo's `launcher/ui/themes`. The log says which: `yw4: themes: 11 (...)` |
| `YW4_FLASH=1` | **Flash detector** (`runtime/src/window.c`): every presented frame also goes into a 320-wide thumbnail, read back one frame later without stalling. A frame where many thumbnail texels are brighter than in both the frame before and after is logged (`yw4: flash: frame N ...` with the area) and the three thumbnails are saved to the screenshot folder (`flash_<frame>_a_before/b_flash/c_after.bmp`, first 40). `YW4_FLASH_THRESHOLD` (brighter by, of 255, default 40) and `YW4_FLASH_MIN` (texels per mille, default 3) tune it. Sees the game's frames, not DLSS-G's generated ones |
| `YW4_MINIMAP_WATCH=1` `YW4_MINIMAP_DIR=path` | **Minimap watch** (`runtime/src/gpu_watch.c`; run it with `python -m tools.dev.minimap`, which also prints the report): every frame, for each of the minimap's own images (340x304, 516x460): the draws into it, its clears, the draws that put it on screen, texture slots with nothing behind them, textures uploaded in that frame, and the image itself read back two frames later (texels lit and opaque, per mille). Rows in `minimap_draws.csv` and `minimap_pixels.csv` in that folder (default `work/minimap`); when a count or the picture drops: an event (`minimap`), the pictures before / blank / after (`minimap_<frame>_<size>_*.bmp`, first 40) and the draws of the frames around it with their textures, vertices and constant buffers (`minimap_<frame>_draws.txt`) |
| `YW4_PERF=0` | Turn off the performance log (on by default: `work/perf/perf_<time>.csv` per frame and a `.txt` summary: frame interval, game work, GPU busy/span from timestamp queries, time in command-list translation and GPU waits, CPU, memory; every 600 frames stderr also lists each busy guest thread's share of a core; `YW4_PERF_DIR` moves it) |
| `YW4_EXIT_AT=<frame>` | Tests: the game exits cleanly once that frame has been presented (`tools.dev.scene` sets it to the last scheduled frame). At a clean exit the log lists what was scheduled for a frame the run never got to (`yw4: never reached: YW4_SCREENSHOTS frame 900`): screenshots, `YW4_SET_AT`, image dumps, A/B frames |
| (the events file) | Next to each `perf_<time>.csv`, `perf_<time>.jsonl`: one JSON line per thing that happened (screenshot, setting change, stall with its cause, same-frame A/B count, fatal stop, end), written as it happens (`runtime/src/events.h`). The test tools read it instead of the log's text |
| `YW4_PROFILE=1` | Sample where the presenting (main) thread is every millisecond (Windows; `YW4_PROFILE=submit`: the threads that submit GPU work), from frame `YW4_PROFILE_FROM` if set; `work/perf/profile_<time>.txt`, named with `python -m tools.yw4.profile` |
| `YW4_PROFILE_THREAD=<n>` | With `YW4_PROFILE=submit`: sample only guest thread n (the number in the performance report's thread lines; the busiest render thread is usually 20) |
| `YW4_PROFILE=hitch` | Sample every guest thread but keep only the samples of frames longer than `YW4_PROFILE_HITCH_MS` (default 100): what the game did in a freeze. Each kept frame is logged (`yw4: profile: frame N took M ms`) |
| `YW4_PACE=refresh` (`tick`) | How FRAME RATE 30 and 60 are held: by a deadline whose period is a whole number of the display's refreshes (from Quandiy's fork), or by the emulated 60 Hz vsync tick. Unset: refresh at 30, the tick at 60 (measured, decision 0064); `refresh` or `tick` uses that way at both. For comparing the two ([decision 0064](decisions/0064-pacing-tick-or-refresh.md)): the log says which at the first frame (`yw4: pacing: tick ...` / `yw4: pacing: refresh, period 16.667 ms at 120.00 Hz ...`), and each performance summary has a line `pacing <way> at <cap> frames/s: N frames over 25 ms = x%, standard deviation y ms` (over 50 ms at 30) |
| `YW4_STALL_MS=<n>` | Hitches: a `yw4: stall:` line when a frame's work on the GPU thread (its command lists and present) takes over n ms (default 50; 0 = never), with where it went: waiting for the GPU lock, waiting for the GPU, pipelines built, shaders loaded, images made (with their uploads), texture uploads, and what that leaves. Found on 2026-11-02: images freed in bulk every 300 frames (now a few a frame) and an area's few hundred new textures at once. Outside that timing, also a `stall:` line when the window's present plus Reflex's sleep take over 30 ms, a `window: slow present:` line splitting the present, and every swapchain rebuild logs its frame and time |
| `YW4_GPU_DETILE=0` | Textures out of the game's block-linear layout on the CPU (`tegra.c`) only. By default the GPU does it (`runtime/shaders/detile.comp`): it reads a level straight from the game's pool into a 64 MiB ring in video memory, copied into the image after; levels whose rows aren't whole 16-byte pieces, 12-byte texels, and textures that find the ring busy stay on the CPU. An area's 380 new textures: 168-185 ms in one frame before, 105 ms after |
| `YW4_IMAGE_BLOCKS=0` | Every image its own video-memory allocation. By default images up to 16 MiB take slices of shared 64 MiB blocks (`gpu.c` `image_memory`): an allocation each cost ~40 ms of an area's 380 new textures. Every 600 frames a `yw4: vram:` line (with `VK_EXT_memory_budget`) gives the video memory in use, its peak since the last line, the driver's budget, the blocks and the de-tiling ring |
| `YW4_DETILE_CHECK=1` | Every texture the GPU de-tiles is also de-tiled on the CPU and the two compared byte for byte once the GPU is done (`yw4: detile check:` lines every 500 textures and at any difference). Slower |
| `YW4_TEGRA_CHECK=1` | Every texture read out of the game's block-linear layout (`runtime/src/tegra.c`) is done again the general way and compared; `yw4: tegra check:` lines every 2000 reads and at any difference |
| `YW4_WAITPROF=1` | With the performance summary every 600 frames: where the main thread blocked in the kernel (SleepThread, WaitSynchronization, ArbitrateLock, WaitProcessWideKeyAtomic, WaitForAddress), ms per frame and calls per frame per guest call stack |
| `YW4_SHORT_SLEEP=0` | Sleeps under 0.2 ms use Windows' timer again (~0.5 ms at least). By default they yield and check the clock: the game's main thread polls its jobs with `nn::os::SleepThread(1 us)`, and each poll used to oversleep (busy late-game spot, DLSS P, unlimited: 61 -> 77 frames/s) |
| `YW4_LOG=0` | Turn off the log file (on by default: everything printed on stderr is also saved in `work/logs/yw4_<time>.log`; `YW4_LOG_DIR` moves it) |
| `YW4_AUDIO=0` | No sound (the game's audio still runs, timed at 48 kHz) |
| `YW4_AUDIO_DUMP=<file>` | Also save the sound as played: raw PCM16, 48 kHz, the game's channel count (6 = 5.1) |
| `YW4_HEADLESS=1` | No window, no Vulkan (nothing is drawn) |
| `YW4_ASLR_RETRY=1` | Set internally on automatic child respawn if guest memory reservation collides with an early ASLR allocation; prevents retry loops |
| `YW4_WINDOW_SIZE=<w>x<h>` | Window size in pixels at start. Default: 80% of the desktop, 16:9, at least `1280x720`. The settings file keeps the size the player left the window at under the same name; `tools.dev.run` passes `1280x720` when no settings file is used, so test runs stay one size (`runtime/src/window.c`) |
| `YW4_VULKAN_VALIDATION=1` | Turn on the Vulkan validation layer |

| `YW4_SET_AT=<frame>:<NAME>=<value>,...` | Tests: at those presented frames a panel setting changes as the panel would change it (one step at a time until it shows that value; not saved), e.g. `YW4_SET_AT=4000:YW4_ASPECT=32:9,4600:YW4_UPSCALE=1` (`runtime/src/settings.c`) |
| `YW4_SIZE_FREE=0` | Tests: after a resolution, upscaling or aspect-ratio change, free the old size's targets only 8 frames later (the way before 2026-11-10), not at once before the new size's are made |

| `YW4_SHADOWS=game` | The game's own shadow-caster draws; the default is our pass ([decision 0024](decisions/0024-shadow-pass.md), default since 2026-10-29: faster). The settings panel (F1, SHADOW PASS) switches while playing |

## Recording and replaying input

| Variable | What it does |
|---|---|
| `YW4_RECORD=0` | Every input change and capture key is recorded in `work/inputs/rec_<time>.txt` (on by default); this turns it off |
| `YW4_PLAYER_NAME=<name>` | The game's name entry (a new game asks the boy's and the girl's names) answers this at once instead of showing the name popup. In replays the popup isn't shown either (their clock counts frames, which stop while the game waits): they answer "Nate", then "Katie". `YW4_NAME_PROMPT=1` shows the popup in replays too (`runtime/src/swkbd.c`). Its on-screen keyboard shows while a controller is in use; `YW4_OSK=1` shows it with any device (tests: its keys can be clicked) |
| `YW4_REPORT_DIR=<folder>` | Where the overlay's Report a bug saves its zips (default `reports` in the home folder; `runtime/src/bugreport.c`). `YW4_REPORT_OPEN=0`: Send and Show the zip only write the link in the log instead of opening the browser or Explorer (test runs) |
| `YW4_REPLAY=<file>` | Feed a recording back, so a route can be run without a person. While it plays, the game's main loop runs on a clock of exactly 1/60 s per frame and the recording's ticks are taken as frames, so a route ends in the same place every run (`runtime/src/kernel.c` `yw4_replay_frame_clock`); the game's time then follows its frames, not the wall. When the replay ends, real time again, and the keyboard and gamepad work again, so a short recording can just load the save. Text typed into the overlay's fields is recorded as `t <tick> <text>` lines and its editing keys as `T_LEFT`, `T_RIGHT`, `T_HOME`, `T_END`, `T_BACK`, `T_DEL`, `T_DONE` (`runtime/src/textin.h`). Videos play on real time, so during a replay they blink and stutter against the game's frame time (only then) |
| `YW4_REPLAY_CLOCK=real` | The replay on the wall clock instead (before 2026-10-31): routes drift with loading and shader-build times |
| `YW4_MOUSE=0` | The game never takes the mouse: no capture, camera, clicks or wheel (`tools.dev.run` sets it, so the PC can be used during test runs) |
| `YW4_RUMBLE=0` | Turn off controller vibration/rumble (default 1, on; [decision 0058](decisions/0058-controller-rumble.md)) |
| `YW4_RUMBLE_GAIN=<float>` | Scale vibration intensity on the host gamepad (default 1.0; e.g. 0.5 for half strength, 1.5 for stronger rumble) |
| `YW4_RUMBLE_SHAPE=0` | The game's vibration as sent (linear), instead of shaped for PC pads' motors: faint texture dropped, a kick at each swell's start, cut while it fades ([decision 0058](decisions/0058-controller-rumble.md), 2026-11-10) |
| `YW4_RUMBLE_TRIGGERS=0` | Xbox One / Series pads: no trigger-motor kicks for the high band (default on) |
| `YW4_RUMBLE_LOG=1` | A log line per change: what the game asked (both bands' amplitude and frequency) and the motor and trigger speeds sent |
| `YW4_INPUT=2400:1:10` | Scripted presses, `tick:buttons(hex):length`, comma separated; `1` is A |

## Looking inside a frame

| Variable | What it does |
|---|---|
| `YW4_DUMP_IMAGE=<hex addr>[,<hex addr>...]` `YW4_DUMP_IMAGE_AT=<frame>[,<frame>...]` | Read back the images at those guest addresses at that frame (several frames: the file names get `_f<frame>`) (depth, RGBA8, RGBA16F, R11G11B10F): per-layer min/max/cleared share, `work/dump/image_*.pgm`, and raw floats in `image_*.rgbaf` (colour) or `image_*.depthf` (depth). This is the image's last use in the frame |
| `YW4_CAPTURE_FS=<fs key prefix>[,...]` with `YW4_DUMP_IMAGE_AT=<frame>[,...]` | Copy the colour targets right after each draw with that fragment shader in those frames (up to 64), to `work/dump/cap_<n>_<fs>_f<frame>_t<target>.raw`; shows a pass's output before later passes reuse the target. `python -m tools.yw4.capview` makes a contact sheet |
| `YW4_COMPUTE_TRACE=<n>` | Every n frames, the inputs and results of the last dispatch of each compute shader |

Image addresses and shader keys come from the Shift+F11 log. Shaders are named by the FNV-1a hash of their assembly:
`work/shaders/asm/<key>.<stage>.asm` is the original, `work/shaders/glsl/<key>.<stage>` the translation (one GLSL
statement per instruction, with the source as a comment).

## Tracing and probes

`YW4_TRACE_*`, `YW4_PROBE*`, `YW4_WATCH*` (guest write watch with a call stack; one per process) and
`YW4_GPU_TRACE*` are described where they are read in `runtime/src/`. To name a guest address in a log, pipe it
through `python -m tools.yw4.where -`.

Two of them map the engine's frame ([frame.md](frame.md)):

| Variable | What it does |
|---|---|
| `YW4_TRACE_LAYERS=<frame>` | Every layer the model renderer (`f_a45890`) draws while frames `<frame>` to `<frame>+2` are presented: thread, layer kind, key range, mask and submeshes drawn. Maps layer kinds to passes ([frame.md](frame.md)) |
| `YW4_TRACE_RENDER_JOBS=<frame>` | Every job the render threads run while frames `<frame>` to `<frame>+2` are presented: function, its two arguments, the thread. Slows the game a little (a check at every function entry) |
| `YW4_TRACE_DRAW_CALLERS=1` | Each different call stack that records a draw, once per render-target size and program, with the shaders; `python -m tools.yw4.mainview <log>` groups such a log (with `YW4_GPU_TRACE`) into passes with the drawing functions |
| `YW4_TRACE_DRAWLIST=<frame>` | From that frame, the model renderer's draws (`YW4_TRACE_DRAWLIST_MAX`, default 24): what was bound, the submesh record, and where in the draw object, geometry and submesh records the bound addresses and uniform-buffer contents are found (pointer search two levels deep), the engine's texture slots, the model record's texture table and a texture view's words. `YW4_TRACE_DRAWLIST_COLOURS=3` keeps only draws into 3 colour targets (the G-buffer). Slow while it prints |
