# Rules for Gemini in this repo

Read `CLAUDE.md` first: it describes the project (a static recompilation of Yo-kai Watch 4++ for PC) and its
non-negotiable rules. This file adds the rules that past work here got wrong. Follow them exactly.

## Never
- **Never edit anything under `work/`.** `work/recomp/*.c` is generated by `python -m recomp.translate` and is
  overwritten on every run. To change generated code, change the recompiler (`recomp/*.py`) or
  `recomp/overrides.toml` (`[[hook]]` with `offset` = function start, optional `at` = an instruction inside it),
  then re-run `python -m recomp.translate`.
- **Never guess a fact about the game** (an offset, a struct field, what a flag means, which icon is which button).
  Read the generated C in `work/recomp/` (read-only), or measure it with a script. If you can't verify it, say
  "unverified" in your report; don't write it as fact in a comment.
- **Never change behaviour you weren't asked to change**: default key bindings, existing settings, unrelated
  functions. No "while I was here" rewrites.
- **Never delete existing comments** or rewrite working code just to restyle it.
- **Never commit or push.** Leave changes in the working tree for review.
- Never add game data, keys, dumps or generated C to the repo (CLAUDE.md rule 1).

## Always
- Match the surrounding code: same comment density and tone, same naming, C17, 4-space indent, 120 columns.
- Keep the change as small as the task allows. Ask before adding a dependency or touching more than ~3 files.
- Build: `python -m recomp.build` (close every `yw4.exe` first; the build can't replace a running exe).
- Recompiler changes: also run `python -m pytest tests -q`.
- Test in the game, not just the build. Use `python -m tools.dev.run` (see `tools/dev/README.md`). Pass
  `YW4_SETTINGS_FILE=work/test_x.ini` so the owner's `settings.ini` is not changed, then delete that file.
  Screenshots: `--shots <frames> --shot-dir work/shots_x`. Panel keys in a replay: `k <tick> F1|F2|UP|DOWN|LEFT|RIGHT|ENTER`.
- Edit C files with your editor tools, not with a Python heredoc (a `"\n"` in a C string turns into a real
  newline and breaks the build).
- New environment variables go into `docs/debugging.md`. A real design choice gets a short record in
  `docs/decisions/` (next free number).

## Report at the end, in this shape
1. **Changed:** files and a one-line reason each.
2. **Verified:** what you checked and how (build, tests, which run, which screenshot showed what).
3. **Not verified / guessed:** every assumption left open. An empty list means you checked everything.
4. **Left for the owner:** anything that needs a human (playing, a controller, a mouse).
Plain English, short sentences. If something failed, say so first.
